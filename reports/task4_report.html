Task 4: Containerized Prediction Service with Daily Retraining

Final task of the Nova TV case study. The LightGBM model from Task 2 is packaged into a Dockerized REST API with a retraining pipeline, model versioning, and rollback capability.

1. What Was Built

+-------------------+ | REST API | FastAPI on port 8000 | (app/api.py) | POST /predict, GET /health, GET /model-info +--------+----------+ | +--------+----------+ | Predictor | Loads latest model from latest.txt | (app/predict.py)| Runs feature engineering + inference +--------+----------+ | +--------+----------+ | Feature Eng. | Shared by train AND predict paths | (app/feature_ | Temporal + own/competitor + encoding | engineering.py) | +-------------------+ +---------------------------------------------+ | Orchestration (scripts/) | | retrain.sh -- daily: download, train, save| | rollback.sh -- revert latest.txt pointer | +---------------------------------------------+ +---------------------------------------------+ | Versioning (models/) | | model_YYYYMMDD_HHMMSS.pkl + metadata | | feature_cols.json + latest.txt | +---------------------------------------------+
Design principle: The feature engineering pipeline is the single source of truth -- used identically by both the training path and the prediction path. This guarantees that the features the model was trained on are exactly the features used at inference time.

2. System Components

2.1 Feature Engineering (app/feature_engineering.py)

Extracted from task2_model.py into a reusable module. Accepts a DataFrame with raw data.csv columns and returns engineered features.

StepWhat it doesWhy
1. Temporal features Derives hour, day_of_week, month, is_weekend, is_prime_time Task 1 EDA showed prime time and day-of-week are the strongest non-prior signals
2. Own vs competitor For each row, extracts its channel's f_1..f_12 as own_f_N and computes comp_mean_f_N + comp_max_f_N from the other 3 channels Task 1 showed negative cross-channel correlations; the model learns zero-sum dynamics
3. Categorical encoding Label-encodes genre (own_f_10) and country (own_f_11), filling NaN with "MISSING" Linear regression needs numeric input; LightGBM would handle strings natively but pipeline must serve both
4. Channel one-hot One-hot encodes channel_id into channel_3, channel_4, channel_9, channel_54 Gives the model explicit channel identity beyond the own-feature signal
5. Feature selection Returns 42 columns in the exact order the model expects The trained model's feature_names_in_ must match

2.2 Training Pipeline (app/train.py)

CLI script invoked by retrain.sh. python -m app.train [--data-url URL]

StepWhat it does
1. Data acquisitionDownloads from URL or loads local data/data.csv
2. Feature engineeringCalls the shared engineer_features()
3. Time splitLast 30 days as validation; earlier data as training
4. Model trainingLightGBM with early stopping (50 rounds), 1000 trees max
5. Versioned saveWrites model_TIMESTAMP.pkl, metadata_TIMESTAMP.json, feature_cols.json, and updates latest.txt

2.3 Prediction Service (app/predict.py + app/api.py)

EndpointMethodWhat it returns
/predict POST Predicted share_15_54 for each requested (timeslot, channel) pair. Looks up programming features from the stored dataset by finding the closest matching timeslot.
/health GET {"status": "ok", "model_loaded": true}
/model-info GET Current model timestamp and validation metrics (MAE, RMSE, R²)
Prediction flow: The API loads data/data.csv on each request (~0.2s for 34k rows). For each requested timeslot, it finds the closest matching row in the stored data by minimizing absolute time difference, then runs the model on that row's features. In production this would join against a live programming schedule database instead of scanning CSV.

2.4 Orchestration Scripts

ScriptWhat it does
scripts/retrain.sh [DATA_URL]
  1. Remembers current model from latest.txt
  2. Runs python -m app.train
  3. If training fails (non-zero exit): restores the previous model
  4. Prints old and new model filenames for audit
scripts/rollback.sh MODEL_FILE Rewrites latest.txt to point to the specified model version. Lists available models if the requested one is not found.

3. Model Versioning

Models are timestamped files. No models are ever deleted -- all versions retained.

models/
├── model_20240101_000000.pkl       ← Seed model from Task 2
├── metadata_20240101_000000.json   ← Placeholder metadata
├── model_20240102_030000.pkl       ← First retrained model
├── metadata_20240102_030000.json   ← MAE, RMSE, R², n_train, n_val
├── model_20240103_030000.pkl       ← Second retrained model
├── metadata_20240103_030000.json
├── feature_cols.json               ← 42 feature column names
└── latest.txt                      ← "model_20240103_030000.pkl"
Rollback mechanism: latest.txt is the single point of indirection. To roll back, change this file to point to an older model. The API picks up the change on restart (or could be extended to watch the file and hot-reload).

5. Design Decisions & Justification

LightGBM over neural networks

Trains in seconds on CPU. Handles missing values natively (Channel 9's 100% null features are treated as a learnable signal, not imputed away). Inference is microseconds per prediction -- a tree traversal, not a forward pass. Explainable via SHAP. Grinsztajn et al. (2022) showed tree-based models consistently outperform deep learning on tabular data at this scale.

Timestamp-based versioning over git

Simpler for this use case. Each model is a self-contained .pkl file with accompanying metadata JSON. Rollback is a single-line file write. No branching, no merge conflicts, no git history to manage. Would switch to a model registry (MLflow, DVC) at larger scale.

FastAPI over Flask

Automatic OpenAPI docs at /docs. Built-in request validation via Pydantic models. Async support (though this workload is CPU-bound and wouldn't benefit much). Modern, actively maintained, and widely adopted for ML serving.

Shell script orchestration over Airflow/Prefect

This is a single model with a single daily job. A workflow engine is overkill. retrain.sh is 30 lines of bash -- readable, auditable, and trivially schedulable via cron. Would migrate to a workflow engine if the pipeline grew to multiple models with complex dependencies.

6. Known Limitations & Production Hardening

#LimitationCurrent behaviorProduction fix
1 CSV loaded on every /predict call 10 MB file parsed each request (~0.2s) Pre-load into memory at startup. Index by timeslot. Or accept full feature row in request body.
2 LabelEncoders re-fit each time Stable on static data; breaks if new categories appear Save fitted encoders alongside model. Map unseen categories to "UNKNOWN".
3 Binary pass/fail quality gate Only rolls back on crash, not on metrics regression Compare old/new metadata MAE. Reject if regression >20%.
4 Nearest-timeslot feature lookup Uses closest matching timeslot if exact not found Accept full feature row in request, or join against live schedule DB.
5 No authentication Open API API key middleware, request logging, rate limiting.
6 Single-container deployment API and training share resources Split into API server + training worker with shared model volume.
7 feature_cols.json overwritten Old models break if feature list changes Version feature_cols.json alongside each model.

7. How to Run

Option A: Docker (one command)

cd task4
docker-compose up --build

API at http://localhost:8000. Docs at http://localhost:8000/docs.

Option B: Local Python

cd task4
pip install -r requirements.txt
pip install pytest httpx       # for tests

# Verify
pytest tests/ -v

# Start
uvicorn app.api:app --host 0.0.0.0 --port 8000

Example API calls

# Health check
curl http://localhost:8000/health

# Model metadata
curl http://localhost:8000/model-info

# Predict share for Channel 3 at a specific timeslot
curl -X POST http://localhost:8000/predict \
  -H "Content-Type: application/json" \
  -d '{"timeslot_datetime_from":["2024-01-10T20:00:00"],"channel_id":[3]}'

# Retrain from fresh data
./scripts/retrain.sh https://example.com/updated_data.csv

# Rollback
./scripts/rollback.sh model_20240101_000000.pkl
